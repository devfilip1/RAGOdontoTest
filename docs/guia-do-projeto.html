Guia do projeto

RAG OdontoTest

Um assistente que responde perguntas de clientes da clínica com base em um PDF de 3 páginas, e uma avaliação que mede se ele está respondendo certo.

O projeto tem duas metades. O assistente busca no material da clínica os trechos mais parecidos com a pergunta e pede a um modelo local que responda só com eles. A avaliação faz 60 perguntas com resposta conhecida, confere cada resposta e guarda o resultado, para você saber se uma mudança melhorou ou piorou o assistente.

97,8%nota geral hoje; era 54,3% antes das melhorias
60perguntas no gabarito: 46 de trabalho e 14 reservadas
37/38perguntas em que a busca traz a evidência certa
1,0 stempo típico de uma resposta; era 2,1 s

Tudo roda no seu computador, com o Ollama. Nada é enviado para serviços externos.

Como funciona

1. Preparação do material, uma vez

O PDF é lido e dividido conforme uma estratégia declarada em config/strategies.yaml. A estratégia em uso é a divisão por seção: cada tratamento vira um trecho que começa com o próprio nome e traz junto o preço, o tempo e o resultado dele. Cada estratégia gera o seu índice em data/index/<nome>/, e os trechos são guardados de duas formas: como vetores, para a busca por significado, e como texto, para a busca por palavras.

PDF da clínica8 procedimentos e os diferenciaisdata/source
→
Divisão por seção11 trechos: 8 tratamentos, a abertura, os diferenciais e o conviteingest.py
→
Índice vetorialChroma, com o modelo nomic-embed-text
Arquivo de trechoschunks.json, para a busca lexical

2. A cada pergunta

A busca segue o experimento indicado na linha assistant: de config/experiments.yaml. Hoje é o section_hybrid: duas buscas rodam sobre os mesmos trechos e cada uma contribui com os seus 2 melhores. Sem os repetidos, de 2 a 4 trechos entram no prompt, ordenados pela posição que tiveram nas duas buscas. A busca por palavras ignora acentos, plural e palavras vazias, e traduz o jeito de falar do cliente para o do material: "custa" também procura "investimento".

Pergunta"Quanto custa o clareamento?"
→
Busca vetorial2 trechos de significado parecido
Busca lexical (BM25)2 trechos com as mesmas palavras
→
Junçãode 2 a 4 trechos, sem repetição
→
llama3regras fixas, depois os trechos e a pergunta
→
Resposta

As regras de atendimento dizem ao modelo para copiar os valores como estão, usar só o trecho do tratamento perguntado, não fazer contas e, quando a resposta não está no material, responder "Não tenho essa informação no momento." em vez de inventar.

Tudo isso está em assistant/pipeline.py, em duas funções: retrieve() faz as buscas e answer() gera a resposta. O chat e a avaliação chamam essas mesmas funções, então a avaliação mede exatamente o assistente que o cliente usa.

A conferência principal não usa modelo. Ela extrai os valores da resposta e compara com o gabarito: "R$ 1.500", "1500 reais" e "mil e quinhentos reais" contam como o mesmo valor.

Preparar o ambiente

Você já fez isso nesta máquina. Fica aqui para quando precisar refazer ou instalar em outro computador. Requer Python 3.14 e o Ollama aberto.

PowerShell, na raiz do projeto
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt

ollama pull llama3
ollama pull nomic-embed-text

python -m assistant.ingest      # cria o índice em data/index/

Toda vez que abrir um terminal novo, ative o ambiente com .venv\Scripts\Activate.ps1. Sem isso o comando python não é encontrado.

Usar o assistente

Conversar no terminal
python -m assistant.chat        # digite "sair" para encerrar

Atalhos

Os comandos do dia a dia têm apelidos, que funcionam sem ativar o ambiente virtual. O Makefile tem os mesmos nomes, para quem tiver o make instalado.

PowerShell, na raiz do projeto
.\run.ps1 help                  # lista os 15 atalhos
.\run.ps1 chat
.\run.ps1 experiments           # compara as configurações de busca
.\run.ps1 eval --label o-que-mudei

A resposta aparece enquanto é escrita. O assistente não lembra das perguntas anteriores: cada pergunta é respondida sozinha.

Rode python -m assistant.ingest de novo sempre que trocar o PDF ou mudar a divisão. Sem isso o assistente continua respondendo com o índice antigo.

Como testar

Há três tipos de teste, e cada um responde a uma pergunta diferente.

ComandoRespondeTempoPrecisa do Ollama
pytestO código está certo? São 308 testes: a configuração, a divisão do PDF, a busca, a bancada, a extração de valores, as métricas e o histórico.3 sNão
pytest -m integrationO assistente de verdade funciona? Confere se os índices estão em dia com o PDF e com as estratégias, se ele responde um preço certo e se recusa o que não sabe.8 sSim
python -m evaluation experimentsQual configuração de busca traz o trecho certo em mais perguntas? Compara todos os experimentos em uma tabela, sem gerar respostas.10 sSim
python -m evaluation retrievalEm quais perguntas a busca do assistente falha? Detalha um experimento.5 sSim
python -m evaluation kb-checkO índice de uma estratégia está íntegro? Procura trechos duplicados, fatos separados do nome do procedimento e texto corrompido.3 sNão
python -m evaluation run --smoke --no-judgeO assistente responde certo? Versão rápida, com 10 perguntas.20 sSim
python -m evaluation run --no-judgeO assistente responde certo? Versão completa, com 46 perguntas.1 minSim
python -m evaluation runO mesmo, mais as notas de comportamento dadas pelo juiz.6 minSim

No dia a dia você vai usar quase só a avaliação. O pytest importa quando você mexer no código.

Um erro, lido por inteiro

Este é o erro que motivou a avaliação, como aparecia antes das melhorias. O placar mostra cada pergunta errada assim:

✗ clareamento-preco-01 (Falha de resposta) Pergunta: Quanto custa o clareamento? Resposta: O clareamento dental é um procedimento que custa entre R$ 120 e R$ 250. Esperado: preço: R$ 500 a R$ 1.500 Detalhe: faltou: preço; valor inesperado: R$ 120, R$ 250; valor de outro procedimento

O valor respondido é o da limpeza. A causa "falha de resposta" diz que o trecho certo foi recuperado e mesmo assim a resposta saiu errada. O motivo estava no índice: havia um trecho que terminava com o preço da limpeza e começava o título "Clareamento Dental". A divisão por seção acabou com isso, e hoje a resposta é "O clareamento dental custa R$ 500 a R$ 1.500."

O bloco Comportamento (juiz) é a opinião do llama3 sobre tom, objetividade e convite ao agendamento. Ele não entra na nota geral e ainda não foi conferido com você.

Bancada de busca

A avaliação acima mede a resposta. A bancada mede só a busca, para escolher como dividir e buscar o material. Ela roda cada experimento de config/experiments.yaml sobre as 38 perguntas com resposta e mostra uma tabela. Estes são os números de 10/10/2026.

ExperimentoDivisãoBuscaTrue RateScoreAncoradaTempo
section_hybrid (em uso)por seçãohíbrida37/380,67100%39 ms
section_bm25por seçãopor palavras37/380,65100%33 ms
page_hybridpor páginahíbrida37/380,6481,8%36 ms
section_vectorpor seçãovetorial35/380,6697,0%35 ms
recursive_500_200_hybrid500 caractereshíbrida31/380,6781,8%35 ms
  • True Rate é a coluna que mede acerto: perguntas em que todas as evidências do gabarito vieram entre os trechos.
  • Score é a similaridade média entre a pergunta e os trechos. Ele não mede acerto: a divisão por 500 caracteres tem o mesmo Score da divisão por seção e erra 6 perguntas a mais.
  • Ancorada diz se o trecho com a resposta também traz o nome do tratamento.

Duas opções foram medidas e não adotadas. Com threshold de 0,6, a evidência deixou de chegar em mais 2 perguntas (35/38). Com HyDE, o True Rate ficou igual (37/38) e a busca passou de 39 ms para cerca de 1,8 s por pergunta. As duas ficaram como exemplo comentado no arquivo de experimentos.

Trocar a configuração do assistente

Em config/experiments.yaml, a linha assistant: diz qual experimento o chat usa. Para adotar outro, troque o nome e confirme com a avaliação da resposta, porque a bancada não vê o que o modelo responde.

Medir a resposta de um experimento antes de adotar
python -m evaluation run --no-judge --experiment page_hybrid

Cada execução da bancada grava dois arquivos CSV em evaluation/runs/experiments/: a tabela, e uma linha por pergunta, que mostra onde cada experimento erra.

Ciclo de melhoria

É assim que o projeto foi pensado para ser usado daqui em diante.

  1. Faça uma mudança de cada vezPor exemplo, uma regra do prompt em assistant/pipeline.py. Com duas mudanças juntas você não sabe qual ajudou.
  2. Recrie os índices, se mudou uma estratégia ou o PDFpython -m assistant.ingest
  3. Se a mudança é de busca, compare na bancadapython -m evaluation kb-checkpython -m evaluation experiments
  4. Rode a avaliação com um rótulopython -m evaluation run --no-judge --label o-que-mudeiO placar termina com a comparação contra a referência: regressões primeiro, depois as métricas e as melhorias.
  5. Olhe as regressões antes da notaUma mudança pode subir a nota geral e fazer errar perguntas que antes acertava.
  6. Se a mudança ficou, ela vira a nova referênciapython -m evaluation baseline set
Outros comandosPara quê
python -m evaluation listVer todas as execuções gravadas e qual é a referência.
python -m evaluation compare A BComparar duas execuções quaisquer pelo id.
python -m evaluation run --experiment NOMEAvaliar a resposta com outro experimento, sem editar o arquivo.

Mapa de arquivos

config.py

O que não é parâmetro de experimento: caminhos, modelos, as palavras ignoradas e os sinônimos da busca por palavras, a temperatura e o limite de tamanho da resposta.

settings.py

Lê e valida config/strategies.yaml e config/experiments.yaml. Um erro de digitação nesses arquivos é recusado aqui, com a mensagem do que corrigir.

index.py

Onde fica o índice de cada estratégia e se ele ainda corresponde à estratégia declarada e ao PDF. É o que impede usar um índice desatualizado.

ingest.py

Lê o PDF, limpa o texto e divide conforme a estratégia (por seção, por caracteres ou por página). Cria um índice por estratégia, sem tocar nos outros.

pipeline.py

O assistente em si. Guarda as regras de atendimento (o prompt) e as funções retrieve(), que faz a busca conforme o experimento (tipo de busca, quantidade de trechos, threshold, HyDE), answer(), que monta o prompt e chama o modelo, e stream_answer(), que entrega a resposta aos poucos.

chat.py

O laço de conversa no terminal. Só lê a pergunta e imprime a resposta enquanto ela é escrita.

data/gabarito.json

As 60 perguntas, com os fatos esperados e a linha do PDF onde está a resposta. É o arquivo mais importante da avaliação, e o único que você edita à mão.

cli.py

Os comandos: run, compare, baseline, list, kb-check, validate, calibrate.

dataset.py

Carrega e valida o gabarito, e separa os recortes: trabalho, reservado e reduzido.

normalize.py

Extrai dinheiro e prazos de um texto, incluindo números por extenso, e os deixa comparáveis.

answer_metrics.py

Confere a resposta: fatos presentes, valores estranhos, valores fora dos trechos, recusa e regras de atendimento. A lista de frases de recusa fica aqui.

retrieval_metrics.py

Confere a busca: a evidência veio, em que posição, e com o nome do procedimento junto.

diagnose.py

Decide a causa de cada pergunta errada.

runner.py

Roda as perguntas no assistente, uma a uma, e monta o resultado de cada uma. Trata a execução interrompida.

aggregate.py

Transforma os resultados em notas: geral, por métrica, por tipo de pergunta e por procedimento.

history.py

Grava e lê as execuções e a referência.

compare.py

Calcula a diferença entre duas execuções: métricas, regressões e melhorias.

report.py

Desenha o placar no terminal e escreve o report.md.

judge.py

O juiz: as rubricas de tom, objetividade, agendamento, relevância e fidelidade, e a chamada ao modelo.

calibrate.py

Gera a amostra para você avaliar e calcula quanto o juiz concorda com você.

kb_checks.py

As verificações do índice que não usam modelo.

experiments.py

A bancada: roda cada experimento sobre o gabarito, calcula True Rate, Score, evidência ancorada e tempo, ordena e grava os CSV.

runs/

Uma pasta por execução, com run.json e report.md, mais o baseline.json, que aponta a referência. É o histórico da evolução do assistente.

README.md

O manual da avaliação, com mais detalhe do que este guia.

unit/

Um arquivo de teste para cada módulo da avaliação, mais os do assistente: configuração, índice, divisão, busca e prompt. test_shortcuts.py confere que o Makefile e o run.ps1 têm os mesmos atalhos. Rodam sem o Ollama.

unit/conftest.py

Um gabarito pequeno e resultados de exemplo, usados por vários testes.

integration/test_assistant.py

Usa o Ollama e os índices de verdade: confere que cada índice está em dia com a sua estratégia e com o PDF, que um preço sai certo, que ele recusa o que não sabe e que importar os módulos não abre o chat.

fixtures/factual_examples.json

20 respostas com formatos variados de valores e prazos e o veredito esperado. Bom lugar para acrescentar um caso quando a conferência errar.

config/strategies.yaml

As formas de dividir o material. Acrescentar uma estratégia de um tipo existente é só editar este arquivo.

config/experiments.yaml

As configurações de busca e a linha assistant:, que diz qual delas o chat usa.

run.ps1 e Makefile

Os atalhos dos comandos, com os mesmos nomes nos dois.

data/source/OdontoTest.pdf

O material da clínica. É a única fonte de verdade do assistente.

data/index/

Um diretório por estratégia, gerado pelo ingest, com o banco vetorial, os trechos e um manifesto. Fica fora do git e pode ser apagado e recriado.

specs/

A especificação, o plano, as decisões técnicas e as tarefas de cada feature: 001 é a avaliação e 002 é a bancada. Leia research.md para entender por que cada métrica foi feita assim.

README.md

Instalação e comandos principais.

.env.example

Modelo para o .env, caso queira trocar os modelos ou o endereço do Ollama.

requirements.txt

As dependências, com versão fixa.

pytest.ini

Configuração dos testes. Faz o pytest puro pular os de integração.

Cuidados

  • Uma ou duas perguntas de diferença não são melhoria. O llama3 pode mudar o texto de uma resposta entre uma execução e outra, mesmo recebendo os mesmos trechos. Só leve a sério diferenças que se repitam em duas execuções.
  • Um erro conhecido ficou. "Os tratamentos de vocês doem?" não recupera o trecho dos diferenciais ("tecnologia moderna e menos dor"), e a resposta sai fraca. É o único erro das 46 perguntas.
  • "Titânio" foi corrigido por fora. No PDF a palavra está corrompida ("■■■ânio"). A correção está em TEXT_FIXES, no config.py. O certo é corrigir o PDF.
  • A bancada não vê a resposta. Dois experimentos com o mesmo True Rate podem dar respostas de qualidade diferente. Antes de adotar um, rode a avaliação com --experiment.
  • Índice desatualizado é recusado. Se você mudar uma estratégia ou trocar o PDF, o chat e a avaliação param e dizem qual comando rodar.
  • A divisão por seção depende dos títulos. As seções são reconhecidas por linhas com as palavras em maiúscula inicial. Um PDF novo com outro formato pode ser dividido errado: confira sempre com o kb-check.
  • Não olhe a parte reservada durante os ajustes. As 14 perguntas de --holdout existem para confirmar, no fim, que a melhoria vale para perguntas que não guiaram as mudanças. A nota delas hoje é 100% (14 de 14); antes das melhorias era 42,9%.
  • As notas do juiz não são confiáveis. Ele deu 4% de objetividade para respostas de uma ou duas frases. Ignore esse bloco do placar até você avaliar as 20 respostas de evaluation/data/human_labels.json e rodar python -m evaluation calibrate score.
  • O gabarito ainda não foi revisado por você. As perguntas foram escritas a partir do PDF. Dois itens têm uma decisão em aberto no campo notes: fora-botox-01 e adv-desconto-01.
  • A conferência é por valor. Se a resposta atribuir o tempo da limpeza ao clareamento e os dois valores forem fatos válidos para a pergunta, a nota não percebe.
