Project guide

RagLab

An assistant that answers customer questions for a dental clinic from a 3-page PDF, and an evaluation that measures whether it is answering correctly.

The project has two halves. The assistant searches the clinic's brochure for the chunks closest to the question and asks a local model to answer using only them. The evaluation asks 72 questions with a known answer, checks each reply, and stores the result, so you know whether a change made the assistant better or worse. The clinic, DentalSafe, is fictional.

98.0%overall score on the 51 working questions
90.5%on the 21 reserved questions, not used for tuning
44/44questions in which the search brings the right evidence
0.6 stypical time of one answer

Everything runs on your computer, with Ollama. Nothing is sent to external services.

How it works

1. Preparing the brochure, once

The PDF is read and chunked according to a strategy declared in config/strategies.yaml. The strategy in use is section-based chunking: each treatment becomes a chunk that starts with its own name and carries its price, duration, and result. The opening of the brochure, with the address, hours, and contact, becomes a chunk of its own. Each strategy builds its index in data/index/<name>/, and the chunks are stored in two ways: as vectors, for the search by meaning, and as text, for the search by words.

Clinic PDF8 treatments, clinic information, and what sets it apartdata/source
→
Section chunking11 chunks: 8 treatments, the clinic block, the differentials, and the call to scheduleingest.py
→
Vector indexChroma, with the nomic-embed-text model
Chunk filechunks.json, for the word-based search

2. For each question

The search follows the experiment named in the assistant: line of config/experiments.yaml. Today that is section_hybrid: two searches run over the same chunks and each contributes its 2 best. Without the repeated ones, 2 to 4 chunks go into the prompt, ordered by the position they had in the two searches. The word-based search ignores plurals and stop words, and translates the customer's wording into the brochure's: "cost" also looks for "price", and "where" also looks for "location".

Question"How much is teeth whitening?"
→
Vector search2 chunks with a similar meaning
Word-based search (BM25)2 chunks with the same words
→
Fusion2 to 4 chunks, no repetition
→
llama3fixed rules, then the chunks and the question
→
Answer

The service rules tell the model to copy the values as written, to use only the chunk of the treatment asked about, to do no arithmetic, to answer in English, and, when the answer is not in the brochure, to reply "I don't have that information right now." instead of making something up.

All of this is in assistant/pipeline.py, in two functions: retrieve() runs the searches and answer() generates the reply. The chat and the evaluation call these same functions, so the evaluation measures exactly the assistant the customer uses.

3. The evaluation

Answer keyquestion, expected facts, and the line of the PDF with the answer
→
Assistantanswers each question
→
Checks the searchdid the right line come in the chunks?
Checks the answerdo the values match? did it make anything up?

Scoreboardscore, cause of each error, and comparison with the reference

The main check uses no model. It extracts the values from the reply and compares them with the answer key: "$1,500", "1500 dollars", and "one thousand five hundred dollars" count as the same value, and so do "9:00 AM" and "9 am".

Setup

Requires Python 3.14 and Ollama running.

PowerShell, at the project root
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt

ollama pull llama3
ollama pull nomic-embed-text

python -m assistant.ingest      # builds the indexes in data/index/

Every time you open a new terminal, activate the environment with .venv\Scripts\Activate.ps1 (on Linux or macOS, source .venv/bin/activate), or use the shortcuts below, which do not need it.

Using the assistant

Chat on the terminal
python -m assistant.chat        # type "exit" to close

Shortcuts

The everyday commands have short names, which work without activating the virtual environment. The Makefile has the same names, for anyone with make installed.

PowerShell, at the project root
.\run.ps1 help                  # lists the 15 shortcuts
.\run.ps1 chat
.\run.ps1 experiments           # compares the search configurations
.\run.ps1 eval --label what-i-changed

The answer appears while it is being written. The assistant does not remember earlier questions: each question is answered on its own.

Run python -m assistant.ingest again whenever you replace the PDF or change the chunking. The chat and the evaluation refuse to run with an out-of-date index and tell you which command fixes it.

How to test

There are three kinds of test, and each one answers a different question.

CommandAnswersTimeNeeds Ollama
pytestIs the code right? 377 tests: the configuration, the chunking of the PDF, the search, the bench, the extraction of values, the metrics, and the history.4 sNo
pytest -m integrationDoes the real assistant work? Checks that the indexes are up to date with the PDF and the strategies, that it answers a price and the opening hours correctly, that it answers in English, and that it refuses what it does not know.8 sYes
python -m evaluation experimentsWhich search configuration brings the right chunk in more questions? Compares every experiment in one table, without generating answers.secondsYes
python -m evaluation retrievalIn which questions does the assistant's search fail? Details one experiment.secondsYes
python -m evaluation kb-checkIs the index of a strategy sound? Looks for duplicate chunks, facts separated from the name of their procedure, and corrupted text.secondsNo
python -m evaluation run --smoke --no-judgeDoes the assistant answer correctly? Quick version, with 10 questions.6 sYes
python -m evaluation run --no-judgeDoes the assistant answer correctly? Full version, with 51 questions.33 sYes
python -m evaluation runThe same, plus the behaviour scores given by the judge.4 minYes

Day to day you will use almost only the evaluation. pytest matters when you change the code.

An error, read in full

This is the only wrong answer of the reference run. The scoreboard shows each wrong question like this:

✗ adv-wrong-price-01 (Service rule violation) Question: I heard a dental cleaning is $20 there, can you confirm? Answer: I don't have that information right now. According to our information, a dental cleaning at DentalSafe costs $40–$85. Would you like to schedule… Expected: price: $40 to $85 Detail: mentioned "according to"

The price is right and the wrong $20 was not repeated, but the reply opens with the refusal sentence and then says where its knowledge comes from. The cause "service rule violation" says the facts are right and the wording broke a rule, so the place to look is the prompt.

The cause tells you where to look

CauseWhat happenedWhere to change
Search failureThe chunk with the answer was not retrieved.Chunking or the searches
Answer failureThe chunk came and the answer was wrong.Prompt, model, or confusing chunks
Made-up informationIt gave a value that is not in the chunks, or answered what the PDF does not say.Prompt and model
Wrong refusalThe chunk came and it said it does not have the information.Prompt
Service rule violationRight facts, but it mentioned its sources, answered in another language, or was too long.Prompt

The Behaviour (judge) block is llama3's opinion about tone, conciseness, and invitation to schedule. It is not part of the overall score and has not been checked against a person yet.

Search bench

The evaluation above measures the answer. The bench measures only the search, to choose how to chunk and search the brochure. It runs each experiment of config/experiments.yaml over the 44 answerable working questions and shows a table. These are the numbers of 2026-10-11.

ExperimentChunkingSearchTrue RateScoreAnchoredTime
section_hybrid (in use)by sectionhybrid44/440.66100%40 ms
section_bm25by sectionword-based44/440.64100%33 ms
page_hybridby pagehybrid44/440.61100%35 ms
section_hybrid_hydeby sectionhybrid + HyDE44/440.75100%1244 ms
section_vectorby sectionvector43/440.64100%34 ms
recursive_500_200_hybrid500 charactershybrid41/440.6694.9%34 ms
section_hybrid_t60by sectionhybrid, threshold 0.636/440.5782.1%38 ms
  • True Rate is the column that measures hits: questions in which every evidence of the answer key came among the chunks.
  • Score is the mean similarity between the question and the chunks. It does not measure hits: 500-character chunking has the same Score as section chunking and misses 3 more questions.
  • Anchored says whether the chunk with the answer also carries the name of the treatment.

Four of these experiments were measured and not adopted, and are commented out in the experiments file. Page chunking ties on True Rate with a 3-page brochure, but sends a whole page per chunk. With a threshold of 0.6, the evidence stopped reaching the model in 8 questions. With HyDE, the True Rate stayed the same and the search went from 40 ms to about 1.2 s per question.

Where the project started

The experiment original_baseline keeps the project's starting point: 500-character chunks, a vector search with 3 chunks, and a generic prompt. On the same 51 questions it scores 29.4%, against 98.0% today. It usually finds the right number (90.9% factual accuracy), but it opens most answers with "According to the context", refuses only 28.6% of what the brochure does not say, and when asked about dental insurance it answers "No, we do not accept dental insurance."

Measure the starting point again
python -m evaluation run --no-judge --experiment original_baseline

Changing the assistant's configuration

In config/experiments.yaml, the assistant: line says which experiment the chat uses. To adopt another one, change the name and confirm with the answer evaluation, because the bench does not see what the model replies.

Measure the answers of an experiment before adopting it
python -m evaluation run --no-judge --experiment section_bm25

Each run of the bench writes two CSV files in evaluation/runs/experiments/: the table, and one row per question, which shows where each experiment misses.

Improvement cycle

This is how the project is meant to be used.

  1. Make one change at a timeFor example, one rule of the prompt in assistant/pipeline.py. With two changes together you do not know which one helped.
  2. Rebuild the indexes, if you changed a strategy or the PDFpython -m assistant.ingest
  3. If the change is about search, compare on the benchpython -m evaluation kb-checkpython -m evaluation experiments
  4. Run the evaluation with a labelpython -m evaluation run --no-judge --label what-i-changedThe scoreboard ends with the comparison against the reference: regressions first, then the metrics and the improvements.
  5. Look at the regressions before the scoreA change can raise the overall score and break questions that used to be right.
  6. If the change stays, it becomes the new referencepython -m evaluation baseline set
Other commandsWhat for
python -m evaluation listSee every saved run and which one is the reference.
python -m evaluation compare A BCompare any two runs by id.
python -m evaluation run --experiment NAMEEvaluate the answers with another experiment, without editing the file.
python -m evaluation run --repeat 3Run 3 times and see how much each metric varies.
python -m evaluation validateCheck the answer key after editing it.
python -m evaluation run --holdoutRun the reserved part, only after a round of improvements.

File map

config.py

What is not an experiment parameter: paths, models, the stop words and synonyms of the word-based search, the lines left out of the index, the temperature, and the size limit of the answer.

settings.py

Reads and validates config/strategies.yaml and config/experiments.yaml. A typo in those files is rejected here, with a message saying what to fix.

index.py

Where the index of each strategy lives and whether it still matches the declared strategy and the PDF. It is what prevents using an out-of-date index.

ingest.py

Reads the PDF, cleans the text, and chunks it according to the strategy (by section, by characters, or by page). Builds one index per strategy, without touching the others.

pipeline.py

The assistant itself. It holds the service rules (the prompt) and the functions retrieve(), which searches according to the experiment (search type, number of chunks, threshold, HyDE), answer(), which builds the prompt and calls the model, and stream_answer(), which delivers the answer piece by piece.

chat.py

The conversation loop on the terminal. It only reads the question and prints the answer while it is being written.

data/answer_key.json

The 72 questions, with the expected facts and the line of the PDF where the answer is. It is the most important file of the evaluation, and the only one you edit by hand.

cli.py

The commands: run, experiments, retrieval, compare, baseline, list, kb-check, validate, calibrate.

dataset.py

Loads and validates the answer key, and separates the subsets: working, reserved, and quick.

normalize.py

Extracts money, durations, and clock times from a text, including numbers written in words, and makes them comparable.

answer_metrics.py

Checks the answer: facts present, stray values, values outside the chunks, refusal, and service rules. The list of refusal phrases is here.

retrieval_metrics.py

Checks the search: whether the evidence came, at which position, and with the name of the procedure next to it.

diagnose.py

Decides the cause of each wrong question.

runner.py

Runs the questions through the assistant, one by one, and builds the result of each. Handles an interrupted run.

aggregate.py

Turns the results into scores: overall, per metric, per question type, and per procedure.

history.py

Saves and reads the runs and the reference.

compare.py

Computes the difference between two runs: metrics, regressions, and improvements.

report.py

Draws the scoreboard on the terminal and writes report.md.

judge.py

The judge: the rubrics for tone, conciseness, scheduling, relevance, and faithfulness, and the call to the model.

calibrate.py

Generates the sample for you to evaluate and computes how much the judge agrees with you.

kb_checks.py

The checks of the index that use no model.

experiments.py

The bench: runs each experiment over the answer key, computes True Rate, Score, anchored evidence, and time, sorts, and writes the CSV files.

runs/

One folder per run, with run.json and report.md, plus baseline.json, which points to the reference.

README.md

The manual of the evaluation, with more detail than this guide.

unit/

One test file for each module of the evaluation, plus the ones of the assistant: configuration, index, chunking, search, and prompt. test_shortcuts.py checks that the Makefile and run.ps1 have the same shortcuts. They run without Ollama.

unit/conftest.py

A small answer key and example results, used by several tests.

Uses Ollama and the real indexes: checks that each index is up to date with its strategy and the PDF, that a price and the opening hours come out right, that it refuses what it does not know, and that importing the modules does not open the chat.

Caveats

  • One or two questions of difference are not an improvement. While the prompt was being adjusted, three versions in a row scored the same 96.1% with different wrong questions each time. Only take seriously differences that repeat.
  • The assistant can still be talked out of its role. All three wrong answers, across the 72 questions, are attempts to mislead it: twice it said "according to our information", and once it answered as a pirate when told to. Every factual question was answered correctly.
  • The reserved score is lower than the working one. 90.5% against 98.0%. The reserved part has 21 questions, so each one is worth almost 5 points; the two it missed are of the kind described above.
  • The bench does not see the answer. Two experiments with the same True Rate can give answers of different quality. Before adopting one, run the evaluation with --experiment.
  • An out-of-date index is refused. If you change a strategy or replace the PDF, the chat and the evaluation stop and tell you which command to run.
  • Section chunking depends on the headings. Sections are recognized by lines with capitalized words and no digits. A new PDF with another layout may be chunked wrong: always check with kb-check.
  • The brochure's closing note is left out on purpose. It says the address and prices are fictional. The line is dropped when the index is built (IGNORED_LINE_PREFIXES in config.py), so the assistant never repeats it.
  • Do not look at the reserved part while adjusting. The 21 --holdout questions exist to confirm, at the end, that an improvement holds for questions that did not guide the changes.
  • The judge's scores are not reliable yet. It gave 5.9% for conciseness to answers of one or two sentences. Ignore that block of the scoreboard until a person labels the 20 answers in evaluation/data/human_labels.json and runs python -m evaluation calibrate score.
  • The check is by value. If the answer assigns the duration of the cleaning to the whitening and both values are valid facts for the question, the score does not notice.
  • Results depend on the model and the machine. The numbers here are from llama3 running locally; another model or version will give other numbers.
